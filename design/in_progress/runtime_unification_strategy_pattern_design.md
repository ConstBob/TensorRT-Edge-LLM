# Design: Runtime Unification via Strategy Pattern (Two-Phase)

Generated by /office-hours on 2026-03-21
Branch: main
Repo: drive-llm (TensorRT Edge-LLM)
Status: APPROVED
Mode: Builder

## Problem Statement

TensorRT Edge-LLM has two completely independent runtime classes — `LLMInferenceRuntime` (~1,046 lines) and `LLMInferenceSpecDecodeRuntime` (~1,805 lines) — with no shared base class. They share ~40-50% conceptual logic (constructor setup, tokenizer, embeddings, multimodal runners, KV cache management) but are implemented as fully separate codebases.

Every new feature (Qwen3 Omni Talker, audio multimodal, LoRA, new model families) must be implemented twice. Bugs fixed in one runtime are missed in the other. The spec-decode runtime is missing sampling parameters, audio support, and public system prompt API that the standard runtime has.

As new decoding modes emerge (P-EAGLE, n-gram, MTP), the current architecture would require a third runtime fork — or more conditionals in an already complex class.

## What Makes This Cool

Replacing two 1,000+ line classes with a single runtime + pluggable decoding strategies. New decoding algorithms become new strategy classes — zero changes to the core runtime. The architecture becomes extensible by addition, not modification.

## Constraints

- **Human review required** for all changes — PRs must be reviewable
- **Codebase must stay functional** at every merge point
- **Two PRs maximum** — team prefers larger coherent changes over many small ones
- **Existing design doc** for nullable-draft approach already exists and team has seen it
- **Active parallel development** — Qwen3-VL, audio, Mamba features landing concurrently
- **Edge platform deployment** — memory efficiency matters (Jetson, DRIVE Thor)
- **C++17** — no C++20 concepts; use virtual interfaces
- **Single-threaded runtime** — all `LLMRuntime` and `DecodingStrategy` methods are called from a single thread per runtime instance. CUDA stream synchronization is the caller's responsibility. No internal locking.
- **Error handling** — strategy methods return `bool` (success/failure). No exceptions across the strategy interface boundary (consistent with existing codebase style). **[ADVERSARIAL #20]** "Consistent state" on failure means: tensor shapes and memory pointers remain valid; tensor contents may be stale/partial. The runtime will not attempt to use tensor contents after a strategy failure — it aborts the current request. Strategies are not required to implement rollback semantics (too expensive for GPU tensors).
- **[ADVERSARIAL #6] Batch sampling constraint** — all sequences in a batch share sampling parameters (temperature, topK, topP). Per-sequence sampling is not supported. This is an existing architectural constraint inherited from the current runtime design.

## Premises

1. The dual-runtime design is the root cause of double implementation — **AGREED**
2. A single unified runtime with pluggable decoding strategy is the right target — **AGREED**
3. The current design doc (nullable draft) is a stepping stone, not the end state — **AGREED**
4. SpecDecodeRuntime's execution flow (prefill → draft → verify → accept) should be preserved as a strategy implementation — **AGREED**
5. New decoding modes are coming and the architecture must accommodate them — **AGREED**

## Approaches Considered

### Approach A: Strategy Pattern (Clean Break)
Single `LLMRuntime` + `DecodingStrategy` interface in one large refactor.
- Effort: L (human: ~3 weeks / CC: ~4 hours)
- Pros: Cleanest result, one pass
- Cons: One massive PR, unreviewable

### Approach B: Nullable Draft (Design Doc As-Is)
Follow existing design doc. SpecDecodeRuntime becomes single runtime with optional draft.
- Effort: M (human: ~1 week / CC: ~1 hour)
- Pros: Fast, design doc exists
- Cons: Null checks proliferate. Not the target architecture. Adding third decoding mode means more conditionals.

### Approach C: Two-Phase — Consolidate then Strategize (CHOSEN)
Phase 1: Land design doc as-is (nullable draft, single runtime).
Phase 2: Refactor into strategy pattern.
- Effort: M + M (human: ~1 week + ~2 weeks / CC: ~1 hour + ~2 hours)
- Pros: Two reviewable PRs. Immediate relief from duplication. Strategy pattern refactors one codebase instead of two.
- Cons: Phase 1 code is partially throwaway. Two rounds of review.

### Phase 2: Strategize (PR 2) — Extract Decoding Strategies

**2.1 Define the DecodingStrategy interface:**

```cpp
// cpp/runtime/decodingStrategy.h

namespace edgellm::rt {

/// [ADVERSARIAL #9] Construction-time context for CUDA graph capture.
/// Separate from DecodingContext because graph capture happens once during
/// construction, not per-request. Contains max-capacity values for sizing.
struct GraphCaptureContext {
    int32_t maxBatchSize;
    int32_t maxInputLen;

    // Engine runner (base model) — for capturing base decode graphs
    LLMEngineRunner& baseEngineRunner;

    // Shared tensor refs — for binding graph inputs/outputs
    Tensor& logitsOutput;
    Tensor& samplingIndices;
    Tensor& samplingScores;
    Tensor& samplingWorkspace;

    // LoRA weight names — iterate to capture per-LoRA graphs
    std::vector<std::string> const& loraWeightNames;

    cudaStream_t stream;
};

/// Context shared between runtime and strategy during a generation session.
/// Mutability contract:
///   - Read-only by strategy: batchSize, maxGenerateLength, temperature, topP, topK,
///     disableSpecDecode
///   - Writable by strategy: logitsOutput, samplingIndices, samplingScores,
///     samplingWorkspace (these are scratch buffers the strategy fills each step)
///   - Read-only references: inputsEmbeds (set by runtime before each step),
///     baseKVCache (managed by engine runner), baseEngineRunner
/// [ADVERSARIAL #6] All sequences in a batch share sampling parameters.
/// Per-sequence sampling is not supported.
struct DecodingContext {
    int32_t batchSize;
    int32_t maxGenerateLength;
    float temperature;
    float topP;
    int32_t topK;

    // [ADVERSARIAL #18] Per-request flag: if true, EAGLE strategy falls back
    // to vanilla decoding for this request. Enables per-request mode switching
    // without swapping strategy objects.
    bool disableSpecDecode;

    // Shared tensors (owned by LLMRuntime)
    Tensor const& inputsEmbeds;   // Read-only: runtime fills before each step
    Tensor& logitsOutput;          // Writable: strategy fills with model output
    Tensor& samplingIndices;       // Writable: strategy fills with sampled token IDs
    Tensor& samplingScores;        // Writable: strategy fills with token scores
    Tensor& samplingWorkspace;     // Writable: scratch space for sampling kernels

    // KV cache state (managed by engine runner internals)
    LinearKVCache& baseKVCache;

    // Engine runner (base model) — strategy calls forward() on this
    LLMEngineRunner& baseEngineRunner;

    cudaStream_t stream;
};

/// Abstract interface for decoding strategies.
class DecodingStrategy {
public:
    virtual ~DecodingStrategy() = default;

    /// Called once after prefill to set up strategy-specific state.
    /// Returns false on failure (e.g., draft model load error).
    virtual bool initialize(DecodingContext& ctx) = 0;

    /// Run one decoding iteration. Returns number of new tokens generated.
    /// For vanilla: always 1. For spec decode: 1 to maxAcceptLength.
    /// Returns -1 on error.
    /// [ADVERSARIAL #7] Error semantics: on failure (-1), the strategy logs the
    /// specific error internally (draft failure, base model failure, sampling
    /// error, etc.). The runtime does not distinguish error types — it always
    /// aborts the current request on -1. Distinct failure modes are captured
    /// in logs, not in the return value.
    virtual int32_t decodeStep(DecodingContext& ctx) = 0;

    /// Allocate strategy-specific tensors. Called during runtime construction.
    /// [ADVERSARIAL #14] Strategy implementations use construction-time config
    /// (passed to their constructor, e.g., EagleDraftingConfig) plus these
    /// base-model parameters to determine tensor sizes. The three params here
    /// are NOT sufficient alone — strategy-specific config is also needed.
    virtual bool allocateTensors(int32_t maxBatchSize, int32_t maxInputLen,
                                  cudaStream_t stream) = 0;

    /// Capture strategy-specific CUDA graphs. Each strategy captures only its
    /// own graphs — vanilla captures the base decode graph, EAGLE captures
    /// draft proposal + accept + base verification graphs. The runtime calls
    /// this once after construction; the strategy is responsible for iterating
    /// over batch sizes and LoRA configs internally.
    /// [ENG REVIEW] Uses GraphCaptureContext (construction-time state), NOT
    /// DecodingContext (per-request state). Separates lifecycles cleanly.
    virtual bool captureCudaGraphs(GraphCaptureContext& gctx) = 0;

    /// Handle batch eviction (remove finished sequences). No-op for vanilla.
    /// [ADVERSARIAL #17] Returns bool (not void) — existing performBatchEvict
    /// returns bool and the generation loop checks it. CUDA kernel failures
    /// during compactKVCache/compactTensorBatch must be propagated.
    virtual bool onBatchEvict(Tensor const& batchMapping, int32_t newBatchSize,
                               cudaStream_t stream) { return true; }

    /// Return strategy-specific metrics via base class pointer.
    /// [ENG REVIEW] Changed from std::variant to inheritance to avoid
    /// hard-coding strategy types in the base interface.
    virtual std::unique_ptr<metrics::DecodingMetrics> getMetrics() const = 0;
};

} // namespace edgellm::rt
```

## Resolved Design Decisions

- **DecodingContext granularity:** Context struct with explicit mutability annotations (see interface definition above). Struct is preferred over individual tensors — reduces parameter count and makes adding new shared state a non-breaking change.
- **[ADVERSARIAL #19] Metrics reporting:** ~~`std::variant` approach~~ **Superseded by [ENG REVIEW] below** — uses `DecodingMetrics` base class with `unique_ptr` return. See the `[ENG REVIEW] Metrics interface` entry below for the authoritative design.
- **CUDA graph capture:** Part of the strategy interface. Each strategy captures its own graphs because graph topology is fundamentally different per strategy (vanilla: 1 graph per batch size; EAGLE: 4 graph types × batch sizes × accept lengths). Runtime calls `captureCudaGraphs()` once after construction.
- **Per-request decode mode switching:** `EagleSpecDecodingStrategy` internally checks `ctx.disableSpecDecode` (added to `DecodingContext` per ADVERSARIAL #18) and falls back to vanilla decoding. This preserves the current behavior where a single runtime instance handles both vanilla and EAGLE requests. The strategy is constructor-level (which algorithm), but per-request fallback is preserved within the EAGLE strategy. **[ADVERSARIAL #15]** Known limitation: there is no mid-generation circuit breaker. If the draft model produces garbage mid-sequence (all tokens rejected for N consecutive rounds), the system continues wasting time on draft proposals for the remainder of the sequence. The `enableSpecDecode` flag is checked once at request start and does not change during the generation loop. A future enhancement could add a consecutive-low-acceptance threshold to trigger mid-generation fallback.
- **[ENG REVIEW] GraphCaptureContext vs DecodingContext:** CUDA graph capture uses `GraphCaptureContext` (construction-time: maxBatchSize, engine runner refs, shared tensor refs). Per-request decoding uses `DecodingContext` (session state: batchSize, temperature, topK, topP, writable tensors). These are separate structs with separate lifecycles.
- **[ENG REVIEW] Metrics interface:** Uses `DecodingMetrics` base class with `LLMGenerationMetrics` and `EagleGenerationMetrics` as subclasses, returned via `std::unique_ptr<DecodingMetrics>`. Callers use `dynamic_cast` for strategy-specific fields. Truly extensible — adding a new strategy never touches the base interface.
- **[ENG REVIEW] allocateTensors sizing:** Strategy self-sizes from its own construction-time config (e.g., `EagleDraftingConfig`). Runtime passes only base model info (maxBatchSize, maxInputLen, stream). Strategy knows its own tensor requirements.
- **[ENG REVIEW] Dynamic tree sizing (future):** `EagleDraftingConfig` will gain a `TreeSizePolicy` mapping batch size → tree config. Tensors allocated for max tree size; CUDA graph selected at runtime by (batchSize, treeConfig) key. Documented as Phase 2 enhancement.
- **Bitwise comparison testing:** Required per success criteria. Phase 1 must include comparison tests between old `LLMInferenceRuntime` output and unified runtime vanilla output. "Bitwise-identical" means identical given the same hardware, same CUDA graph capture state, and same input. Minor floating-point divergence due to kernel launch order changes is acceptable only if documented and the delta is below 1e-5 relative tolerance.

## Success Criteria

- Single runtime class handles both vanilla and spec-decode inference
- Adding a new decoding strategy (e.g., P-EAGLE) requires only a new strategy class — zero changes to `LLMRuntime`
- No-draft mode allocates zero draft-specific GPU memory
- All existing tests pass without modification (after updating construction calls)
- Vanilla path produces bitwise-identical output to the old `LLMInferenceRuntime` (same hardware, same graph state). If specific code paths change kernel order, document WHY and allow 1e-5 relative tolerance for those specific outputs only.
- **[ADVERSARIAL #13]** Mamba/hybrid models (Nemotron Nano V2) are **in-scope** for bitwise comparison. SSM state restore path is being ported from the standard runtime, and any subtle difference in initialization order, tensor layout, or stream synchronization could cause divergence. Include Mamba model in the bitwise test matrix.
- **[ENG REVIEW]** Performance gate: vanilla decode latency within 2% of baseline, spec-decode throughput within 2%, peak GPU memory within 5%. Run existing benchmarks before and after each PR.
- **[ENG REVIEW]** Memory validation: no-draft runtime peak GPU memory < spec-decode runtime peak GPU memory (verify draft tensor savings)
