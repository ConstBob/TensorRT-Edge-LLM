= Tokenizer Architecture
{nbsp}
:description: Tokenizer subsystem architecture across Python export, chat-template processing, and C++ runtime encode/decode

== Overview

The tokenizer subsystem spans Python export and C++ runtime. It owns the
runtime artifact contract, load/encode/decode lifecycle, and the boundary
between generic tokenizer logic and model-family adapters.

The design rule is: *adapt model-family token formats during export so
the C++ runtime consumes one stable HuggingFace-style artifact contract*.
Family token semantics are documented in link:model_formats.adoc[model_formats.adoc].

== Model Applicability

[cols="1,2", options="header"]
|===
| Model Family | Tokenizer Path

| Generic HuggingFace BPE families
| Standard `save_pretrained` export; runtime consumes artifacts unchanged.

| SentencePiece-based families
| Export preserves whitespace semantics in HuggingFace-compatible artifacts.

| Explicit-template families such as Phi-4 multimodal
| Tokenizer is saved normally; a checked-in template replaces unreliable auto-extraction.
|===

== Architecture

[mermaid]
----
flowchart LR
    SRC[Source checkpoint assets] --> EXP[Python export adapters]
    EXP --> TJ[tokenizer.json]
    EXP --> TC[tokenizer_config.json]
    EXP --> CT[processed_chat_template.json]
    TJ --> RT[C++ Tokenizer::loadFromHF]
    TC --> RT
    CT --> RT
----

=== SentencePiece Background

Many LLM tokenizers are trained with SentencePiece, which serializes a
vocabulary and normalization rules as a binary `.model` file. HuggingFace
Fast tokenizer format (`tokenizer.json`) can represent the runtime
tokenization contract in portable JSON. During export, Edge-LLM adapts
supported source formats so the C++ runtime has one artifact contract.
The original `.model` file may be copied as a source sidecar, but the
engine builder and runtime do not currently consume it.

=== Runtime Artifact Contract

`tokenizer.json`:: Primary tokenizer definition consumed by runtime:
pre-tokenizer configuration, model vocabulary/merges, and added tokens.

`tokenizer_config.json`:: Special-token IDs, max length, and the original
chat-template string when present.

`processed_chat_template.json`:: Runtime-friendly chat template with
role prefixes/suffixes, generation prompt, and optional default system prompt.

Export may also preserve source tokenizer sidecars such as `tokenizer.model`
or `special_tokens_map.json` for provenance or compatibility with Python
tooling. They are not part of the current engine-builder copy set or C++
runtime load path.

== Design

=== Python Export Flow

Export starts from `tensorrt-edgellm-export` / `tensorrt_edgellm/scripts/export.py`.
The generic path saves the HuggingFace tokenizer directly and derives a
processed chat template from metadata. Adapter paths convert incompatible
layouts into the same HuggingFace-style artifact set and persist an explicit
chat template when auto-extraction is unreliable.

=== C++ Runtime Flow

==== Initialization

`Tokenizer::loadFromHF(...)` loads `tokenizer.json`, reads special-token
metadata, constructs the pretokenizer/token-encoder pipeline, loads
`processed_chat_template.json`, and fails fast on malformed or missing
artifacts.

==== Encode Path

[mermaid]
----
flowchart TD
    TXT[Formatted prompt text] --> PART[Partition special tokens]
    PART --> PRE[Pretokenizer sequence]
    PRE --> ENC[TokenEncoder]
    ENC --> IDS[Token IDs]
----

Encoding performs optional BOS insertion, longest-match special-token
partitioning, pretokenization, vocabulary lookup, and optional EOS insertion.

==== Decode Path

Decode maps token IDs back to pieces via the reverse vocabulary,
optionally skips special tokens, and concatenates pieces into text.
Whitespace-sensitive families depend on exported token pieces preserving the
same spacing behavior as the source tokenizer.

==== Chat Template Application

Before encoding, runtime applies `processed_chat_template.json`: each
role contributes a prefix/suffix pair, optional content-type format
strings handle multimodal content, and a generation prompt cues assistant
output.

=== Core Runtime Components

==== Pretokenizer
Splits text partitions through supported primitives such as `Sequence` and
`RegexSplit`.

==== Token Encoder
Owns vocabulary lookup and reverse decode mapping. Source formats that
require special handling are converted during export.

== Code Touchpoints

[cols="2,3", options="header"]
|===
| File | Responsibilities

| `tensorrt_edgellm/chat_template.py`
| Chat-template extraction, template validation, and processed-template generation.

| `experimental/server/parsing/tool_chat_template.py`
| Tool-aware server request formatting for agentic workloads.

| `tensorrt_edgellm/chat_templates/`
| Checked-in explicit chat-template data for incompatible families.

| `tensorrt_edgellm/checkpoint/checkpoint_utils.py`
| Checkpoint/config loading helpers and runtime sidecar writing used by export.

| `tensorrt_edgellm/scripts/export.py`
| Export entry point that writes tokenizer artifacts and processed chat templates.

| `cpp/builder/llmBuilder.cpp`
| Engine-builder copy policy for tokenizer runtime artifacts.

| `cpp/tokenizer/tokenizer.{h,cpp}`
| Runtime load, special-token partitioning, encode/decode, and chat-template application.

| `cpp/tokenizer/preTokenizer.{h,cpp}`
| Sequence and regex-split pretokenizer primitives.

| `cpp/tokenizer/tokenEncoder.{h,cpp}`
| Vocabulary encode/decode.
|===

== Testing

- Exported tokenizer versus source tokenizer encode parity.
- Chat-template parity between Python export and C++ formatted text.
- Round-trip decode sanity for whitespace/control-token-sensitive families.
- Deterministic first-token generation on a short prompt before deeper runtime debugging.
