= Tokenizer Model-Format Support
{nbsp}
:description: Model-family tokenizer and prompt-format support rules

== Support Rules

[cols="1,2,2", options="header"]
|===
| Family type | Tokenizer adaptation | Prompt contract

| HuggingFace-compatible
| Preserve `tokenizer.json` and tokenizer metadata.
| Copy the provider `chat_template.jinja` and named Jinja templates verbatim.
Pantor Inja parses them directly when the runtime loads the model.

| Converted tokenizer
| Export a runtime-compatible tokenizer while preserving special-token IDs and whitespace semantics.
| Preserve and apply the source checkpoint's Jinja template.

| No provider Jinja
| Preserve or generate the tokenizer normally.
| Select an explicit `chat_template.model` manual renderer; never infer role prefixes.

| Provider raw processor
| Preserve the provider tokenizer and identify its processor class.
| Apply its explicit content-normalization contract before the provider Jinja;
reject unsupported content.
|===

== Adding a Family

1. Verify tokenizer encode/decode parity against the provider checkpoint.
2. Inspect the provider Jinja and all supported `apply_chat_template` inputs.
3. Add an explicit native renderer only when the model has no Jinja contract.
4. Compare complete formatted strings for system, multi-turn, media,
   reasoning, tools, tool results, and generation prompts.
5. Run end-to-end inference after prompt parity succeeds.

Edge-LLM does not own model-family Jinja copies. Template updates arrive with
the checkpoint and are preserved during export.
